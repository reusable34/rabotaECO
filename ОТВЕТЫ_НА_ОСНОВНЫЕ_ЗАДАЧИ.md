## 3. Структура базы данных

### Общее описание
База данных спроектирована для системы управления экологическими требованиями клиентов. Используется **PostgreSQL 15** с нормализованной структурой (**3NF** - третья нормальная форма).

### Таблицы и их назначение:

#### 1. **users** (Пользователи системы)
**Назначение:** Хранение данных всех пользователей (администраторы, менеджеры, специалисты, клиенты)

**Поля:**
- `id` (PK, integer)
- `name` (string 255)
- `email` (string 255, UNIQUE)
- `password_hash` (string 255)
- `role` (string 50) - admin, manager, specialist, client
- `client_id` (FK, integer, nullable)
- `auth_key` (string 32)
- `created_at`, `updated_at` (integer)

**Почему:** Разделение пользователей и клиентов позволяет одному пользователю работать с несколькими клиентами (для менеджеров) или привязывать пользователя к конкретному клиенту.

#### 2. **categories** (Категории НВОС)
**Назначение:** Справочник категорий негативного воздействия на окружающую среду (I, II, III, IV)

**Поля:**
- `id` (PK, integer)
- `title` (string 255)
- `description` (text)

**Почему:** Категория НВОС определяет набор требований для клиента. Вынесена в отдельную таблицу для нормализации и возможности расширения.

#### 3. **clients** (Клиенты)
**Назначение:** Компании, для которых формируются экологические требования

**Поля:**
- `id` (PK, integer)
- `name` (string 255)
- `category_id` (FK, integer)
- `has_well` (boolean) - Есть скважина
- `has_river` (boolean) - Есть река/озеро
- `has_byproduct` (boolean) - Есть побочный продукт
- `responsible_person` (string 255, nullable)
- `created_at`, `updated_at` (integer)

**Почему:** Параметры `has_well`, `has_river`, `has_byproduct` влияют на автоматическое формирование требований. Вынесены в отдельные поля для удобства запросов и индексации.

#### 4. **requirements** (Экологические требования)
**Назначение:** Требования, которые должны выполнить клиенты (формируются автоматически или добавляются вручную)

**Поля:**
- `id` (PK, integer)
- `client_id` (FK, integer)
- `title` (string 1000) - Название требования
- `status` (string 50) - pending, in_progress, completed, not_completed
- `deadline` (date, nullable)
- `basis` (text, nullable) - Основание (например, "КоАП РФ 8.21 ч.1")
- `artifacts` (text, nullable) - JSON массив артефактов
- `document_year` (integer, nullable)
- `responsible_person` (string 255, nullable)
- `created_at`, `updated_at` (integer)

**Почему:** Требования - центральная сущность системы. Поля `basis` и `artifacts` хранят ссылки на нормативные акты и необходимые документы.

#### 5. **documents** (Документы)
**Назначение:** Файлы документов клиентов (разрешения, отчёты, паспорта и т.д.)

**Поля:**
- `id` (PK, integer)
- `client_id` (FK, integer)
- `file_path` (string 500)
- `type` (string 100, nullable)
- `status` (string 50) - pending, approved, rejected
- `created_at`, `updated_at` (integer)

**Почему:** Документы хранятся отдельно от требований, так как один документ может относиться к нескольким требованиям. Файлы физически хранятся в файловой системе.

#### 6. **contracts** (Договоры и акты)
**Назначение:** Договоры на оказание услуг и акты выполненных работ

**Поля:**
- `id` (PK, integer)
- `client_id` (FK, integer)
- `number` (string 100)
- `status` (string 50) - draft, active, completed, cancelled
- `date` (date)
- `created_at`, `updated_at` (integer)

#### 7. **events** (События календаря)
**Назначение:** События и дедлайны для календаря отчётности

**Поля:**
- `id` (PK, integer)
- `client_id` (FK, integer)
- `title` (string 255)
- `date` (date)
- `completed` (boolean)
- `created_at`, `updated_at` (integer)

#### 8. **risks** (Риски по КоАП)
**Назначение:** Штрафы и риски за невыполнение требований

**Поля:**
- `id` (PK, integer)
- `requirement_id` (FK, integer)
- `article` (string 100) - Статья КоАП
- `fine_min` (decimal) - Минимальный штраф
- `fine_max` (decimal) - Максимальный штраф

**Почему:** Риски привязаны к конкретным требованиям. Одно требование может иметь несколько статей КоАП.

#### 9. **npa** (Справочник НПА)
**Назначение:** Справочник нормативно-правовых актов для админ-панели

**Поля:**
- `id` (PK, integer)
- `code` (string 100) - Код НПА (например, "ФЗ-89", "КоАП РФ 8.2")
- `title` (string 500)
- `link` (string 1000, nullable)
- `block` (string 100, nullable) - Блок: Отходы, Выбросы, Водопользование
- `created_at`, `updated_at` (integer)

#### 10. **audit_log** (Лог действий)
**Назначение:** Аудит действий пользователей для безопасности и отчётности

**Поля:**
- `id` (PK, integer)
- `user_id` (FK, integer)
- `entity_type` (string 100) - Тип сущности
- `entity_id` (integer)
- `action` (string 50) - create, update, delete, view
- `timestamp` (integer)

### Связи между таблицами (Foreign Keys):
```
users.client_id → clients.id (nullable)
clients.category_id → categories.id
requirements.client_id → clients.id
documents.client_id → clients.id
contracts.client_id → clients.id
events.client_id → clients.id
risks.requirement_id → requirements.id
audit_log.user_id → users.id
```

### Индексы:
- Все внешние ключи проиндексированы
- `users.email` (UNIQUE) - для быстрого поиска при авторизации
- `requirements.status`, `requirements.deadline` - для фильтрации и сортировки
- `events.date` - для календаря
- `npa.code`, `npa.block` - для поиска в справочнике

### Нормализация:
Структура соответствует **3NF** (третья нормальная форма):
- Нет транзитивных зависимостей
- Каждая сущность в отдельной таблице
- Минимум дублирования данных
- Связи через внешние ключи

## 6. Интегрированные данные по клиенту

### Демо-клиент
В системе создан демо-клиент с полным набором данных для тестирования.

### Данные клиента:

#### Базовая информация:
- **Название:** "Демо-клиент"
- **Категория НВОС:** II
- **Параметры:**
  - Есть скважина (`has_well = true`)
  - Нет реки (`has_river = false`)
  - Есть побочный продукт (`has_byproduct = true`)
- **Ответственное лицо:** Указано

#### Автоматически сформированные требования:
На основе категории и параметров автоматически создаются требования через `RequirementGeneratorService`:

**Для категории II с параметрами (скважина + побочный продукт):**
- Базовые требования категории II (18 требований)
- + Лицензия на право пользования недрами (из-за скважины)
- + Технические условия "Удобрения органические..." (из-за побочного продукта)

**Итого:** ~20 требований с разными статусами:
- `completed` - выполненные
- `in_progress` - в работе
- `pending` - ожидание
- `not_completed` - не выполнено

**Примеры требований:**
- Журналы учета движения отходов
- Журналы учета стационарных источников выбросов
- Статотчетность по форме 2-ТП (воздух)
- Статотчетность по форме 2-ТП (отходы)
- Декларация о плате за НВОС
- Отчет по программе ПЭК
- Инвентаризация выбросов
- Инвентаризация отходов
- Паспорта на отходы I-IV класса
- НООЛР
- НДВ
- Экспертное заключение на проект НДВ
- СЭЗ на проект НДВ
- План НМУ
- ППЭК
- ДВОС (для II категории)
- Лицензия на недра
- Технические условия на удобрения
