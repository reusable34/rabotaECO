# Несоответствия ТЗ - что нужно доработать

## 🔴 Критические несоответствия

### 1. Роль "Специалист проектного отдела"
**ТЗ:** "Специалист проектного отдела: доступ только к своим проектам"
**Статус:** ❌ Роль есть в модели, но нет реализации логики доступа
- Роль `specialist` определена в `User` модели
- Нет логики фильтрации по проектам
- Нет понятия "проект" в системе (только клиенты)

**Что нужно:**
- Определить, что такое "проект" (возможно, это связь specialist -> requirements или specialist -> clients)
- Реализовать фильтрацию доступа для specialist роли
- Добавить проверки в контроллерах

---

### 2. Чат-бот / Обратный звонок
**ТЗ:** "Есть возможность общения через чат бот или заказать обратный звонок"
**Статус:** ❌ Полностью отсутствует

**Что нужно:**
- Добавить компонент чата на фронтенде
- Реализовать API для отправки сообщений
- Добавить функционал заказа обратного звонка
- Интеграция с внешним сервисом (Telegram Bot API или другой)

---

### 3. Загрузка документов с аудитом
**ТЗ:** "Здесь может быть функционал погрузить с аудитом (доп плата) и без аудита"
**Статус:** ❌ Нет опции выбора аудита при загрузке

**Текущая реализация:**
- Есть загрузка документов (`/document/upload`)
- Нет поля `with_audit` или подобного
- Нет логики обработки аудита

**Что нужно:**
- Добавить чекбокс "С аудитом" при загрузке документа
- Добавить поле в модель `Document` (например, `needs_audit`, `audit_status`)
- Реализовать логику обработки аудита (возможно, отдельный статус документа)

---

## 🟡 Важные несоответствия

### 4. Динамический календарь
**ТЗ:** "Календарь был динамический, сдали отчеты, даты закрыты и выставлены новые на новый период"
**Статус:** ⚠️ Частично реализовано

**Текущая реализация:**
- Есть календарь событий
- Можно отмечать события как выполненные
- НЕТ автоматического создания новых дат после сдачи отчетов

**Что нужно:**
- При изменении статуса требования на "completed" автоматически создавать новое событие на следующий период
- Логика должна учитывать периодичность отчетов (годовая, квартальная, месячная)

---

### 5. RLS (Row-Level Security) в БД
**ТЗ:** "RLS-политики в БД. RLS в БД (обязательное): каждая строка привязана к client_id и/или site_id"
**Статус:** ⚠️ Реализовано только на уровне приложения

**Текущая реализация:**
- Фильтрация по `client_id` в контроллерах (уровень приложения)
- НЕТ PostgreSQL RLS policies на уровне БД

**Что нужно:**
- Создать RLS policies в PostgreSQL для всех таблиц
- Включить RLS на таблицах: `requirements`, `documents`, `contracts`, `events`, `risks`
- Политики должны проверять `client_id` пользователя

---

### 6. Интеграция с Bubble (учетная система)
**ТЗ:** "API-интеграции с учётной системой (Бабл) для статусов договоров/счетов/актов"
**Статус:** ❌ Полностью отсутствует

**Что нужно:**
- Определить API Bubble для получения статусов
- Реализовать синхронизацию статусов договоров/счетов/актов
- Добавить периодическую задачу (cron) для синхронизации
- Обработка ошибок и повторные попытки

---

## 🟢 Мелкие несоответствия

### 7. Анкета клиента
**ТЗ:** "При заведении нового клиента, формируется анкета, часть информации по клиенту загружается автоматически, а часть сотрудник вносит руками"
**Статус:** ⚠️ Есть форма создания клиента, но нет полноценной анкеты

**Текущая реализация:**
- Есть форма создания клиента в админ-панели
- Нет структурированной анкеты с разделами
- Нет автоматической загрузки данных из внешних источников

**Что нужно:**
- Создать полноценную форму анкеты с разделами
- Добавить возможность автоматической загрузки данных (если есть источник)

---

### 8. Резервное копирование
**ТЗ:** "Резервное копирование БД и Storage (ежедневно, хранение ≥30 дней)"
**Статус:** ❌ Не реализовано

**Что нужно:**
- Настроить ежедневное резервное копирование PostgreSQL
- Резервное копирование файлового хранилища (`backend/api/storage`)
- Хранение бэкапов ≥30 дней
- Автоматизация через cron или Docker volumes

---

### 9. Аудит действий
**ТЗ:** "Логика действий (загрузка/удаление файлов, смена статусов). Логирование действий"
**Статус:** ⚠️ Частично реализовано

**Текущая реализация:**
- Есть таблица `audit_log` в БД
- НЕТ записи в `audit_log` при действиях пользователей

**Что нужно:**
- Добавить запись в `audit_log` при:
  - Загрузке/удалении файлов
  - Изменении статусов требований/договоров
  - Создании/редактировании клиентов
  - Других критических действиях

---

### 10. Соответствие 152-ФЗ
**ТЗ:** "Хранение персональных данных: учесть 152-ФЗ (минимум — политика, доступы по ролям, аудит)"
**Статус:** ⚠️ Частично реализовано

**Что есть:**
- Доступы по ролям ✅
- Аудит (частично) ⚠️

**Что нужно:**
- Политика обработки персональных данных (документ)
- Согласие на обработку ПД при регистрации
- Возможность удаления ПД по запросу
- Шифрование чувствительных данных
