# Структура базы данных

## Общее описание

База данных спроектирована для системы управления экологическими требованиями клиентов. Используется PostgreSQL 15 с нормализованной структурой (3NF).

## Таблицы и их назначение

### 1. users (Пользователи системы)

**Назначение:** Хранение данных всех пользователей системы (администраторы, менеджеры, специалисты, клиенты).

**Поля:**
- `id` (PK, integer) - Уникальный идентификатор
- `name` (string 255) - Имя пользователя
- `email` (string 255, UNIQUE) - Email (логин)
- `password_hash` (string 255) - Хеш пароля
- `role` (string 50) - Роль: admin, manager, specialist, client
- `client_id` (FK, integer, nullable) - Связь с клиентом (для ролей client, manager)
- `auth_key` (string 32) - Ключ для аутентификации
- `created_at` (integer) - Дата создания
- `updated_at` (integer) - Дата обновления

**Индексы:**
- `idx-users-email` (UNIQUE) - Быстрый поиск по email
- `idx-users-client_id` - Оптимизация запросов по клиенту

**Почему:** Разделение пользователей и клиентов позволяет одному пользователю работать с несколькими клиентами (для менеджеров) или привязывать пользователя к конкретному клиенту.

---

### 2. categories (Категории НВОС)

**Назначение:** Справочник категорий негативного воздействия на окружающую среду (I, II, III, IV).

**Поля:**
- `id` (PK, integer)
- `title` (string 255) - Название категории
- `description` (text) - Описание

**Почему:** Категория НВОС определяет набор требований для клиента. Вынесена в отдельную таблицу для нормализации и возможности расширения.

---

### 3. clients (Клиенты)

**Назначение:** Компании, для которых формируются экологические требования.

**Поля:**
- `id` (PK, integer)
- `name` (string 255) - Название компании
- `category_id` (FK, integer) - Категория НВОС
- `has_well` (boolean) - Есть скважина
- `has_river` (boolean) - Есть река/озеро
- `has_byproduct` (boolean) - Есть побочный продукт (животноводство)
- `responsible_person` (string 255, nullable) - Ответственное лицо (ФИО)
- `created_at` (integer)
- `updated_at` (integer)

**Индексы:**
- `idx-clients-category_id` - Оптимизация фильтрации по категории

**Почему:** Параметры `has_well`, `has_river`, `has_byproduct` влияют на автоматическое формирование требований. Вынесены в отдельные поля для удобства запросов и индексации.

---

### 4. requirements (Экологические требования)

**Назначение:** Требования, которые должны выполнить клиенты (формируются автоматически или добавляются вручную).

**Поля:**
- `id` (PK, integer)
- `client_id` (FK, integer) - Клиент
- `title` (string 500) - Название требования
- `status` (string 50) - Статус: pending, in_progress, completed, not_completed
- `deadline` (date, nullable) - Срок выполнения
- `basis` (text, nullable) - Основание (например, "КоАП РФ 8.21 ч.1")
- `artifacts` (text, nullable) - JSON массив артефактов (документов)
- `document_year` (integer, nullable) - Год документа
- `responsible_person` (string 255, nullable) - Ответственное лицо
- `created_at` (integer)
- `updated_at` (integer)

**Индексы:**
- `idx-requirements-client_id` - Оптимизация запросов по клиенту
- `idx-requirements-status` - Фильтрация по статусу
- `idx-requirements-deadline` - Сортировка по срокам

**Почему:** Требования - центральная сущность системы. Поля `basis` и `artifacts` хранят ссылки на нормативные акты и необходимые документы. JSON для `artifacts` позволяет хранить массив без создания отдельной таблицы.

---

### 5. documents (Документы)

**Назначение:** Файлы документов клиентов (разрешения, отчёты, паспорта и т.д.).

**Поля:**
- `id` (PK, integer)
- `client_id` (FK, integer) - Клиент
- `file_path` (string 500) - Путь к файлу
- `type` (string 100, nullable) - Тип документа
- `status` (string 50) - Статус: pending, approved, rejected
- `created_at` (integer)
- `updated_at` (integer)

**Индексы:**
- `idx-documents-client_id` - Оптимизация запросов по клиенту
- `idx-documents-status` - Фильтрация по статусу

**Почему:** Документы хранятся отдельно от требований, так как один документ может относиться к нескольким требованиям. Файлы физически хранятся в файловой системе, в БД только метаданные.

---

### 6. contracts (Договоры и акты)

**Назначение:** Договоры на оказание услуг и акты выполненных работ.

**Поля:**
- `id` (PK, integer)
- `client_id` (FK, integer) - Клиент
- `number` (string 100) - Номер договора
- `status` (string 50) - Статус: draft, active, completed, cancelled
- `date` (date) - Дата договора
- `created_at` (integer)
- `updated_at` (integer)

**Индексы:**
- `idx-contracts-client_id` - Оптимизация запросов по клиенту
- `idx-contracts-status` - Фильтрация по статусу

**Почему:** Договоры - отдельная бизнес-сущность, не связанная напрямую с требованиями. Может быть несколько договоров с одним клиентом.

---

### 7. events (События календаря)

**Назначение:** События и дедлайны для календаря отчётности.

**Поля:**
- `id` (PK, integer)
- `client_id` (FK, integer) - Клиент
- `title` (string 255) - Название события
- `date` (date) - Дата события
- `completed` (boolean) - Выполнено
- `created_at` (integer)
- `updated_at` (integer)

**Индексы:**
- `idx-events-client_id` - Оптимизация запросов по клиенту
- `idx-events-date` - Сортировка по дате

**Почему:** События могут быть связаны с требованиями, но также могут быть независимыми (например, плановые проверки).

---

### 8. risks (Риски по КоАП)

**Назначение:** Штрафы и риски за невыполнение требований.

**Поля:**
- `id` (PK, integer)
- `requirement_id` (FK, integer) - Требование
- `article` (string 100) - Статья КоАП
- `fine_min` (decimal) - Минимальный штраф
- `fine_max` (decimal) - Максимальный штраф

**Индексы:**
- `idx-risks-requirement_id` - Оптимизация запросов по требованию

**Почему:** Риски привязаны к конкретным требованиям. Одно требование может иметь несколько статей КоАП.

---

### 9. npa (Справочник нормативно-правовых актов)

**Назначение:** Справочник НПА для админ-панели.

**Поля:**
- `id` (PK, integer)
- `code` (string 100) - Код НПА (например, "ФЗ-89", "КоАП РФ 8.2")
- `title` (string 500) - Название
- `link` (string 1000, nullable) - Ссылка на документ
- `block` (string 100, nullable) - Блок (раздел): Отходы, Выбросы, Водопользование
- `created_at` (integer)
- `updated_at` (integer)

**Индексы:**
- `idx-npa-code` - Поиск по коду
- `idx-npa-block` - Фильтрация по блоку

**Почему:** Справочник НПА используется для формирования требований и ссылок в системе. Вынесен в отдельную таблицу для удобства управления через админ-панель.

---

### 10. audit_log (Лог действий)

**Назначение:** Аудит действий пользователей для безопасности и отчётности.

**Поля:**
- `id` (PK, integer)
- `user_id` (FK, integer) - Пользователь
- `entity_type` (string 100) - Тип сущности (client, requirement, document и т.д.)
- `entity_id` (integer) - ID сущности
- `action` (string 50) - Действие: create, update, delete, view
- `timestamp` (integer) - Время действия

**Индексы:**
- `idx-audit_log-user_id` - Фильтрация по пользователю
- `idx-audit_log-entity` - Поиск по сущности (entity_type, entity_id)

**Почему:** Аудит необходим для отслеживания изменений и безопасности системы. Хранится отдельно для производительности основных таблиц.

---

## Связи между таблицами (Foreign Keys)

```
users.client_id → clients.id (nullable, для ролей client/manager)
clients.category_id → categories.id
requirements.client_id → clients.id
documents.client_id → clients.id
contracts.client_id → clients.id
events.client_id → clients.id
risks.requirement_id → requirements.id
audit_log.user_id → users.id
```

**Почему FK:**
- Целостность данных (нельзя удалить клиента, если есть требования)
- Каскадное удаление (при удалении клиента удаляются его требования)
- Оптимизация JOIN запросов

## Индексы

Все внешние ключи проиндексированы для оптимизации запросов. Дополнительные индексы:
- `users.email` (UNIQUE) - для быстрого поиска при авторизации
- `requirements.status`, `requirements.deadline` - для фильтрации и сортировки
- `events.date` - для календаря
- `npa.code`, `npa.block` - для поиска в справочнике

## Нормализация

Структура соответствует 3NF (третья нормальная форма):
- Нет транзитивных зависимостей
- Каждая сущность в отдельной таблице
- Минимум дублирования данных
- Связи через внешние ключи

## Расширяемость

Структура позволяет легко добавить:
- Новые типы документов (через поле `type`)
- Новые статусы (через ENUM или отдельную таблицу)
- Дополнительные поля для клиентов (через миграции)
- Новые роли пользователей (через поле `role`)
